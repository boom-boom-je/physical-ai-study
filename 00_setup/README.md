## 내 답

### 1. 관측 (observation)
- **17차원.** 칸 하나하나는 숫자 하나(스칼라)이고, 17개를 묶은 전체가 하나의 벡터다.
- **Num 0~7: 위치·각도.** 지금 몸이 어디에, 어떤 자세로 있는지 (단위 m, rad)

  | Num | 뜻 |
  |---|---|
  | 0 | 몸통의 높이 (z, m). 처음 높이(0.7m)를 0으로 둔 변화량 |
  | 1 | 몸통의 기울기 각도 (rad) |
  | 2~4 | 뒷다리 허벅지·정강이·발 관절 각도 (rad) |
  | 5~7 | 앞다리 허벅지·정강이·발 관절 각도 (rad) |

- **Num 8~16: 속도·각속도.** 그 위치·각도가 얼마나 빠르게 변하고 있는지 (단위 m/s, rad/s)

  | Num | 뜻 |
  |---|---|
  | 8 | 몸통의 앞뒤(x) 속도 (m/s). +면 앞으로, -면 뒤로 |
  | 9 | 몸통의 위아래(z) 속도 (m/s) |
  | 10 | 몸통 기울기의 각속도 (rad/s) |
  | 11~13 | 뒷다리 허벅지·정강이·발 관절 각속도 (rad/s) |
  | 14~16 | 앞다리 허벅지·정강이·발 관절 각속도 (rad/s) |

- 정리하면 관절 6개 × (각도, 각속도) = 12개에 몸통 5개(높이, 기울기, 앞뒤 속도, 위아래 속도, 기울기 각속도)를 더해 17개다.
- 문서 표에는 기준점이 "front tip(앞 끝)"이라고 쓰여 있다. 하지만 모델 파일(`half_cheetah.xml`)을 보면 `rootx`·`rootz`·`rooty` 관절이 몸통 중심에 붙어 있다. 그래서 0, 1, 8~10번은 발이 아니라 **몸통 전체**의 위치·기울기·속도다.
- 방향은 부호로 나타낸다. 예를 들어 8번이 +면 앞으로, -면 뒤로 움직이는 중이다.
- 위치·각도만으로는 사진 한 장처럼 "지금 어느 쪽으로 움직이는 중인지"를 알 수 없어서 속도도 함께 준다.
- **앞뒤 위치(x)가 빠진 이유:** 트랙의 어디에 있든 달리는 방법은 같아야 하기 때문이다. 자세를 제어하는 데는 높이·기울기·관절 각도와 그 속도만 있으면 되고, 앞뒤 위치는 필요 없다. 오히려 x를 넣으면 멀리 달려갈수록 학습 때 보지 못한 값이 들어와 정책이 헷갈릴 수 있다. 문서도 위치와 무관한 행동(position-agnostic behavior)을 유도하려고 뺀다고 설명한다. 앞으로 가는 **속도**(8번)는 보상과 바로 이어지므로 들어 있다.
- HalfCheetah는 앞뒤(x)와 위아래(z)로만 움직이는 2차원 모델이라 좌우 방향은 없다.

### 2. 행동 (action)
- **6차원, 각 값은 -1 ~ 1** (`Box(-1.0, 1.0, (6,), float32)`). 범위 안의 어떤 실수든 되는 **연속 행동**이다. CartPole은 0과 1 중 하나를 고르는 이산 행동이다.
- 각 값은 관절 6개에 각각 **얼마나 힘을 줄지 정하는 토크**(관절을 돌리는 힘, N·m)다. 부호는 회전 방향이다.

  | Num | 관절 |
  |---|---|
  | 0~2 | 뒷다리 허벅지·정강이·발 |
  | 3~5 | 앞다리 허벅지·정강이·발 |

- **관측과의 관계:** 토크는 회전을 빠르게 하거나 늦추는 힘이다(τ = Iα, F = ma의 회전 버전). 그래서 행동은 먼저 관절 각속도(관측 11~16)를 바꾸고, 그 변화가 쌓여 관절 각도(관측 2~7)가 바뀐다. 예: 행동 0(뒷다리 허벅지 토크) → 관측 11(각속도) → 관측 2(각도).
- 몸통(관측 0, 1, 8~10)에는 모터가 없다. 다리로 바닥을 밀어서 간접적으로만 움직일 수 있다.

### 3. 보상 (reward)
- 매 스텝 보상 = `forward_reward` − `ctrl_cost`
  - `forward_reward` = 1.0 × 몸통의 앞뒤 속도 (m/s). 앞으로 가면 +, 뒤로 밀리면 −다.
  - `ctrl_cost` = 0.1 × (행동 6개 제곱의 합). 힘을 쓸수록 커지는 비용이라, "적은 힘으로 효율적으로 달려라"는 뜻이다.
- 에피소드는 넘어져도 끝나지 않는다 (`terminated`는 항상 False). 1000스텝(시뮬레이션 50초)이 되면 시간 제한으로 `truncated`가 되어 끝난다.
- 에피소드 보상은 이 값을 1000스텝 동안 더한 것이다. 이 과제는 300스텝만 돌려서 그 부분 합이다.
- **랜덤 에이전트의 300스텝 점수가 약 -60 근처인 이유:**
  - 무작위 행동은 -1~1에서 고르게 뽑혀서 제곱의 평균이 1/3이다. 한 스텝 `ctrl_cost` 평균은 0.1 × 6 × 1/3 = 0.2이고, 300스텝이면 약 60이 빠진다.
  - 무작위로 휘저으면 앞뒤로 흔들리기만 해서 `forward_reward`는 평균 0 근처다.
- **실행할 때마다 점수가 다른 이유:** 시드를 정하지 않아서 시작 자세(reset 잡음)와 무작위 행동이 매번 달라진다. `ctrl_cost`는 거의 항상 -60 근처이고, 차이는 대부분 `forward_reward`에서 나온다. 한 스텝이 0.05초라서 `forward_reward`의 합은 **그 판에서 이동한 거리 × 20**이다.
  - 내 GIF에서는 치타가 제자리에서 움찔거리다 뒤로 밀려났다. 뒤로 밀린 만큼 점수가 -60보다 더 낮아진다. 예: 시드 0에서는 2.13m 밀려서 -60 − 43 ≈ -104가 나왔다.
  - 시드를 고정하면 몇 번을 돌려도 같은 점수가 나온다. Project 1에서 시드 3개로 실험하고 평균±표준편차로 보고하는 이유다.

### 4. `body_mass`
- 몸 조각(body)별 질량을 담은 배열이다. 단위는 kg이고 8칸이다.

  | Num | 몸 조각 | 질량 (kg) |
  |---|---|---|
  | 0 | world (세상·바닥) | 0 |
  | 1 | torso (몸통) | 6.25 |
  | 2 | bthigh (뒷다리 허벅지) | 1.54 |
  | 3 | bshin (뒷다리 정강이) | 1.59 |
  | 4 | bfoot (뒷발) | 1.10 |
  | 5 | fthigh (앞다리 허벅지) | 1.44 |
  | 6 | fshin (앞다리 정강이) | 1.20 |
  | 7 | ffoot (앞발) | 0.88 |

- 0번 `world`는 움직이지 않는 세상(바닥 포함)이라 질량이 의미가 없어서 0이다. 몸통은 world에 붙어 있고, 다리 조각은 몸통에서 나무 모양으로 이어진다 (world → 몸통 → 허벅지 → 정강이 → 발).
- 몸통이 전체의 약 45%로 가장 무겁다.
- 합계는 14kg이다. 모델 파일(`half_cheetah.xml`)이 `settotalmass="14"`로 전체 합을 14kg에 맞춘다. 실행할 때마다 뜨는 `settotalmass` 경고는 이 옛 설정 방식이 앞으로 MuJoCo에서 없어질 예정이라는 안내다.
- 질량을 1.5배로 늘리면, 모터의 힘(토크)은 그대로인데 움직여야 할 몸이 무거워져 같은 힘에 덜 가속되고 움직임이 둔해진다 (a = F/m). 바닥을 누르는 힘과 마찰력도 커진다. 그래서 같은 행동이라도 결과가 달라진다.
- Project 1에서는 이 배열에 배율을 곱해 질량을 바꾼다 (0.5~1.5배). 원래 값은 `.copy()`로 저장해 두고 되돌린다. 같은 시드·같은 행동이어도 질량을 1.5배로 바꾸자 300스텝 점수가 -103.8에서 -83.2로 달라졌다.
- **Project 1에서 확인하려는 것:** 기본 질량으로 학습한 정책을 질량·마찰이 바뀐 환경에서 평가해 성능이 얼마나 떨어지는지(견고성) 재고, 도메인 랜덤화로 학습한 정책과 비교한다. 시뮬레이터와 현실의 물리 값 차이 때문에 생기는 sim-to-real 문제를 작게 재현하는 실험이다. 다음 단계인 Project 2는 바뀐 물리 값을 스스로 추정해 적응한다.
